# Renderer Contract — 2D / 3D / Selection

## Purpose

Define the boundary between canonical semantic/kernel state and visual rendering so the product can support high-performance 2D and live 3D without creating two engineering models.

## Core rule

Renderers consume **derived immutable snapshots/primitives** produced from semantic/kernel state. Renderers may own camera, hover, GPU/cache, animation, and temporary interaction state, but never authoritative road/lane/junction geometry.

## Shared derivation flow

```text
Canonical semantic project/scenario
        ↓
Geometry / topology kernel
        ↓
Derived scene snapshot
   ┌───────────────┬───────────────┐
   ↓               ↓               ↓
2D adapter      3D adapter      Export adapter
```

2D and 3D may use different tessellation/representation detail but share semantic ids and engineering results.

## Derived snapshot requirements

Conceptually include:
- snapshot/version id;
- project/scenario id;
- local render origin metadata;
- semantic-object lookup/index;
- road/component boundary geometry;
- surfaces/polygons;
- junction surfaces/corners;
- markings/attachment data;
- lane connection/movement guides when requested;
- asset instances/attachments where relevant;
- validation/selection overlay anchors;
- bounding boxes/extents;
- provenance back to semantic ids.

Exact DTO/module structure is an implementation decision to prove during R1C.

## Semantic identity

Every selectable/rendered engineering primitive must map back to a stable semantic object or derived sub-entity id.

Examples:
- road R01;
- lane R01/L2;
- junction J01;
- corner J01/NE;
- marking M12;
- asset instance A44.

Do not recover selection identity by spatially searching coordinates after a click if the renderer already knows the rendered object's semantic id.

## 2D adapter responsibilities

May handle:
- world→screen transform;
- view-dependent tessellation/simplification;
- line/fill styling;
- hit-test acceleration/indexes;
- labels/dimensions/handles;
- selection/hover visualization;
- basemap/reference composition;
- temporary snap/measure guides.

Must not independently compute:
- lane offsets/width lifecycles;
- junction pavement semantics;
- corner engineering geometry;
- topology/lane connectivity;
- standards validity.

## 3D adapter responsibilities

May handle:
- local-origin coordinate conversion;
- mesh-buffer construction from accepted derived surfaces/sections;
- normals/materials/UVs;
- instanced assets;
- camera/orbit/pan;
- LOD and visibility;
- lighting/shadows/presentation effects;
- selection/hover highlight.

Must not independently decide lane widths, road boundaries, junction connectivity, or engineering dimensions.

## Mesh generation principle

Road 3D should be generated by stitching semantic station/cross-section geometry or equivalent shared kernel outputs, preserving component/lane identities where practical. Avoid extruding one anonymous giant pavement polygon if doing so destroys semantic selection/material/control needed by the product.

Junction surfaces may use triangulated derived polygons, but the semantic junction/topology remains upstream.

## Engineering vs presentation mode

Both modes use the same semantic/derived engineering geometry.

Engineering mode prioritizes:
- neutral materials;
- clear boundaries/markings;
- selection/validation overlays;
- inspectability.

Presentation mode may add:
- richer materials;
- vegetation/vehicle variations;
- lighting/shadows/environment;
- context buildings.

Changing mode must not change engineering geometry or validation.

## Selection synchronization

A shared application-level selection model stores semantic ids. Renderers receive selected ids and highlight their local representations.

Flow:
```text
2D click → semantic id → shared selection state → 3D + hierarchy + properties highlight
3D click → semantic id → shared selection state → 2D + hierarchy + properties highlight
```

Renderer-specific mesh ids are implementation detail.

## Preview interactions

During direct manipulation:
- UI creates a candidate semantic command/parameter state;
- kernel derives preview geometry;
- renderer displays preview;
- final interaction commits one semantic command.

For performance, an approved lightweight preview approximation may exist during drag only if final release/commit always re-derives robust canonical geometry and preview limitations are tested. Preview must not become hidden persisted truth.

## Incremental regeneration

Future performance optimization may track dependency/change sets so only affected geometry is regenerated. Optimization must preserve equivalence with full rebuild.

Required regression:
`incremental rebuild result ≈ full clean rebuild result` within declared derived-geometry tolerance.

## Local rendering origin

Canonical coordinates remain project/engineering coordinates. A derived snapshot declares local render origin O; renderer uses `p_render = p_project - O` before GPU float conversion.

Rules:
- origin change is renderer/project-view state, not geometry edit;
- selection ids do not change when origin changes;
- exported engineering coordinates never use local-render coordinates by mistake;
- 2D/3D can share an origin strategy or use coordinated origins as long as semantic mapping remains stable.

## Basemap/reference composition

The map/reference renderer is a sibling/reference layer, not an engineering renderer. Provider/license capabilities control display/export/cache/digitization according to `MAP_BASEMAP_POLICY.md`.

Engineering geometry can render/export without a basemap.

## Disposable caches

Allowed caches:
- sampled polylines;
- tessellated paths;
- mesh buffers;
- GPU resources;
- spatial hit-test indexes;
- label layout;
- thumbnails.

All are disposable and keyed/versioned against upstream state where needed. Deleting caches must not damage the project.

## Renderer failure handling

A renderer error must not corrupt semantic project state.

If derived geometry cannot render:
- preserve canonical state;
- report affected semantic id/snapshot;
- allow diagnostic fallback where practical;
- never write renderer-repaired coordinates back into the model silently.

## Performance targets

R0/R1 targets are investigation targets, not permanent SLAs. Measure:
- kernel derivation;
- 2D primitive generation;
- 3D mesh generation;
- upload/draw cost;
- hit test/snap query;
- incremental regeneration.

Do not optimize by violating semantic/renderer separation.

## R1C proof requirements

R1C must demonstrate:
- one upstream fixture creates both 2D and 3D;
- matching semantic ids in both views;
- large-coordinate/local-origin stability;
- clean cache rebuild equivalence;
- no duplicated engineering algorithms in renderer modules.

## Architecture invariant

**A renderer may choose how to draw a design, but it may not decide what the design is.**
